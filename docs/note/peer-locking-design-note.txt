배경:
  server는 하나의 UDP socket과 하나의 TUN device를 공유하면서 여러 peer를 관리한다.

  sequence number를 추가하면서 peer별로 다음 상태값을 관리해야 한다.

    serverSendSequence
    lastClientSequence
    lastSeen

  이 값들은 단순 조회값이 아니라 packet 처리 중 계속 변경되는 상태값이다.


고민:
  peer 상태 변경을 어디에서 책임질 것인가?

    1. peerStore 중심 방식
    2. peer 포인터 중심 방식


1. peerStore 중심 방식
----------------------

형태:
  peerStore가 peer map 조회뿐 아니라 sequence 증가, sequence 검증, lastSeen 갱신까지 처리한다.

예:
  s.peers.nextSendSequence(peerID)
  s.peers.acceptClientSequence(peerID, seq)
  s.peers.touch(peerID)

장점:
  peerStore mutex 안에서 map 조회와 상태 변경을 함께 처리할 수 있다.
  외부로 peer 원본 포인터를 오래 노출하지 않아도 된다.
  lock 관리 위치가 peerStore에 모인다.
  현재 구조에서 최소 변경으로 적용하기 쉽다.

단점:
  모든 peer의 상태 변경이 peerStore mutex 하나에 몰릴 수 있다.
  packet 처리량이 많아지면 lock contention이 생길 수 있다.
  peerStore가 단순 저장소를 넘어 peer의 비즈니스 로직까지 가지게 된다.
  이미 peer를 조회한 뒤 다시 peerStore 메서드에 peerID를 넘기는 흐름이 조금 어색하다.

어울리는 상황:
  구현을 단순하게 유지하고 싶을 때.
  peer 수가 많지 않고 packet 처리량이 크지 않을 때.
  상태 변경 규칙을 한 곳에 모으는 것이 더 중요할 때.


2. peer 포인터 중심 방식
-----------------------

형태:
  peerStore는 peer 등록, 조회, 삭제만 담당한다.
  peer 자신의 상태는 peer 내부 mutex로 보호하고 peer 메서드가 직접 변경한다.

예:
  p, ok := s.peers.getByID(peerID)
  p.acceptClientSequence(seq)
  p.nextSendSequence()
  p.touch()

장점:
  peer별 mutex를 사용할 수 있어 peer A의 packet 처리가 peer B를 막지 않는다.
  lock granularity가 작아져 UDP 기반 서버에서 확장성이 좋다.
  peerStore는 registry 역할에 집중하고, peer는 자기 상태를 직접 관리한다.
  sequence, replay window, 통계, 암호화 세션 같은 peer별 상태가 늘어날 때 자연스럽다.

단점:
  peer 원본 포인터가 외부로 노출된다.
  peer 내부 mutex 사용 규칙을 지켜야 한다.
  expire로 map에서 삭제된 peer를 이미 goroutine이 들고 있는 상황의 의미를 정해야 한다.
  필요하면 peer에 closed/expired 같은 상태를 추가해야 할 수 있다.

어울리는 상황:
  peer가 여러 개이고 packet 처리가 자주 발생할 때.
  peer별 상태가 앞으로 더 늘어날 때.
  고성능 UDP VPN/proxy 서버 구조를 고려할 때.


삭제와 포인터에 대한 정리:
  peerStore에서 peer를 delete 하더라도,
  이미 어떤 goroutine이 *peer 포인터를 들고 있으면 Go GC는 그 peer 객체를 바로 해제하지 않는다.

  따라서 메모리 안전성만 보면 문제가 되지 않는다.

  다만 논리적으로는 이미 만료된 peer의 packet을 계속 처리해도 되는지 결정해야 한다.
  필요하면 peer 내부에 expired/closed 상태를 두고 peer mutex 안에서 확인한다.


현재 판단:
  단기적으로는 peerStore 중심 방식이 단순하고 적용하기 쉽다.

  하지만 이 프로젝트는 UDP 기반 VPN 서버이고,
  sequence 검증, keepalive, peer lifecycle, 나중의 replay window 또는 암호화 세션까지 고려하면
  peer 포인터 중심 방식이 더 자연스럽다.

  최종 구조는 다음 방향이 더 적합하다.

    peerStore:
      peer 등록
      peer 조회
      peer 삭제
      byID / byTunnelIP map 관리

    peer:
      lastSeen 갱신
      serverSendSequence 증가
      lastClientSequence 검증/갱신
      나중의 replay window, 통계, 암호화 세션 상태 관리


정리:
  peerStore 중심 방식은 안전하고 단순하다.
  peer 포인터 중심 방식은 더 확장 가능하고 네트워크 서버 구조에 가깝다.

  현재 sequence number를 추가하는 단계에서는,
  peer 내부 mutex를 두고 peer가 자기 상태를 관리하는 방향을 우선 검토한다.
